# Tutorial compatibility smoke stall investigation

Updated: 2026-10-06 · [한국어](Tutorial_Smoke_Stall_20261005.md)

The second launch of `-hellscriptTutorialSmoke` (`-hellscriptTutorialResume`) was reported to fail after about 170 s with `Timed out following the prologue gate: survival lesson target=`, on `origin/main` at `ee5a949c` and on the tutorial chronicle branch. The smoke is a compatibility check of the pre-disclosure v2 flow using an `edictLegacyAccess=true` account. There was more than one cause. Behaviour created by the staged disclosure work (`93d59959`) and later changes collided with stale smoke expectations in four places. All four are fixed and the smoke now passes end to end for the first time (final marker `HELLSCRIPT_TUTORIAL_RUNTIME_SMOKE_OK`). While fixing the fourth, a regression introduced by the first (app) fix was found and fixed as well. During the investigation the chronicle branch (PR #52), the passive tuning (PR #55), the Hunt Edict native port (PR #53) and the tutorial wiring (PR #56) were merged into `main` one after the other, so the final verification was done on a tree that includes all four merges. After the last merge one more intermittent failure showed up, a missed pointer in the F05 step, and the smoke's `Tap` was fixed (section 5). PR #54 was merged before that fix, so the fix and the record of runs 8 to 13 went in a follow-up PR. While it was being prepared, the town model PR #57 (`4fc52dba`) and the pit tutorial PR #58 (`945fa46f`) were merged, so runs 14 and 15 were done on the tree up to #57 and runs 16 to 19 on the tree up to #58.

**State after PR #58.** PR #58 rebuilt the mandatory tutorial (P00) as the pit trial (checkpoint `tutorial-v4`, [the pit tutorial](Pit_Trial_Tutorial.en.md)). The smoke's opening is now `PitAcceptance` in `RuntimeTutorialSmoke.Pit.cs` and its replay is `PitReplay`. `RuntimeTutorialSmoke.Progression.cs`, which this record covers (`ReplayAcceptance`, `FollowProgressiveGate`, `ProgressiveAcceptance`), and the `-hellscriptEdictProgressionSmoke` entry point are gone. So the v2 survival lesson of section 1 and the v3 replay of section 4 no longer run on today's `main`; those two sections stay as the record of the investigation at the time. What still applies to the stretch after the arrival: the picker rule of section 1 (`QuickAllowed`; the pit lesson now counts as `ProgressivePrologue` and hides the picker under the same condition), the smoke handling of sections 2 and 3 (attendance hide, hints hidden after the first rift) and the `Tap` settling of section 5. Runs 1 to 15 in the verification table are on trees from before #58. On the tree with #58 merged the full smoke stopped in the final replay, and one more defect in the app, in the pit trial's replay, was found and fixed (section 6).

## 1. The potion picker in the survival lesson — app, fixed

[HuntEdictWindow.DrawSelectedGroup](../../Assets/HELLSCRIPT/Runtime/Presentation/HuntEdictWindow.Summary.cs) excluded the quick-preset picker of the `Auto potion` group (`survival.potion`) for every account through a group-name check. For new accounts the check was redundant because [HuntEdictProgression.Quick](../../Assets/HELLSCRIPT/Runtime/Core/HuntEdictProgression.cs) already refuses that scope. For legacy accounts `Quick` always returns true, yet the picker disappeared.

The v2 survival lesson (`GameUI.SurvivalLessonStep`) tells legacy accounts to press `edict-quick-picker-global/survival.potion`. The button did not exist, so `LessonTarget` returned null and the gate showed its line without a target. The gate releases input after 2 s, so the player is not trapped, but the line points at a button that does not exist and that way of finishing the lesson is unavailable. The smoke's `FollowGate` waits 120 s for a target and then fails.

The fix removes the group-name check so that `Quick` alone decides. For legacy accounts the `Auto potion` group shows the quick-preset picker first again, like the other groups (the behaviour before `93d59959`). One check was added to `HuntEdictProgressionTests` to pin the two cases of `Quick`.

Judgement: either the picker could be restored or the v2 lesson could be changed. The app picker was restored because `Quick` allows every scope for legacy accounts, the documentation promises that existing accounts keep their access and that in-progress v2 saves finish on the old flow, and the coach tip `death-potion` recommends a preset of this scope. If the intent was that even legacy accounts see only the direct potion options, change the v2 lesson instead of keeping this fix.

Merge conflict: PR #53 moved this condition into `HuntEdictWindow.QuickAllowed` and carried the potion-group exclusion along, which conflicted with PR #54. Its design document records the missing potion picker as the state of the code at the time, not as a decision about legacy accounts. At the merge the port's structure was kept and the two conditions of this fix (`Quick` decides; the v3 prologue has no picker) were moved inside `QuickAllowed`, so the new chip subtitle follows the same rule. The port's contract smoke uses staged accounts only, and its other smokes were adapted to pass with or without a picker, so they are not affected. Because the same exclusion came up independently on two branches, the decision to keep the potion picker for legacy accounts should be confirmed once more in review.

Regression and follow-up fix: the fix as first pushed had a regression, found while writing the replay check. A replay always runs the v3 lesson, but its window still reads the real account. For a legacy account `Quick` is true, so the picker was also drawn in the v3 HP lesson window and hid `edict-option-survival.potionHpPercent`, the control the lesson points at ([screen](TutorialSmokeEvidence20261005/replay-r2-picker-hides-hp-option.png)). Before the fix the potion group had no picker, so that path worked. The same condition now also requires `!ProgressivePrologue`, so the v3 prologue shows direct options only, whatever the account (`ed79f12f`). New accounts and the v2 lesson are unchanged. This is a window condition that EditMode cannot test; the replay check is its test.

## 2. The attendance popup — smoke, fixed

With the picker visible the same run was blocked after the town arrival by the daily attendance window. When the greeting closes, `GameUI.TickAttendance` opens the attendance window as designed, and `ShowAttendance` cancels the town walk in progress with `Town.Cancel()`. The step waiting for the walk to the rift keeper timed out. The smoke now saves "hide for today" for both attendance popups and closes an open one, the way several other smokes do. Why the same smoke passed on 2026-09-30 without this was not investigated.

## 3. The edict notice card — smoke, fixed

The F07 step stalled next. `TryEdictNotice` (`93d59959`) shows one notice card in town whenever a result settles. After the F06 step the town went idle and the `Retry with modified settings` card opened and blocked the walk to the training ground. Steps F05 to F07 drive the same guides by hand, so `hintsHidden` is turned on once the first rift is over and the hero is back in town. It is set after the first rift so that the existing check that no automatic popup interrupts that rift keeps its meaning.

## 4. The replay — smoke, fixed

Runs 3 and 4 stopped in the final replay segment. `GameController.BeginTutorial(replay)` builds a fresh account with `GameStore.NewAccount`, so even a legacy account's replay always runs the v3 flow. The first v3 segment has a single dialogue, while the smoke waited for `tutorial-continue` twice as in v2. The second wait timed out after 15 s.

`ReplayAcceptance` in `RuntimeTutorialSmoke.Progression.cs` now follows the replay through the v3 lesson. `FollowProgressiveGate` presses the comparison's observation areas (A/B), the final choice and the HP threshold number field with real pointers. It checks that the final choice and the HP threshold are saved on the replay's own hero, and that a replay played to the end leaves the real account's equipment, economy and progression unchanged. It copies the choreography of `ProgressiveAcceptance` without that smoke's first-run checks. The two were not merged into one loop, because that would mean re-verifying `ProgressiveAcceptance` (the v3 first-run check). A timeout in the new helper leaves the same screen and window-list evidence as `Until`.

The replay alone was run three times on a clone-only shortcut (not in the repository). The first run stalled in the HP lesson, with no target for 60 s. The second, with timeout diagnostics added, showed the regression of section 1. After the fix the third run passed in 1 min 43 s.

## 5. Window rebuild and the pointer — smoke, fixed

On the tree with PR #56 merged, the second launch sometimes stopped in the F05 step with `Pointer blocked: edict-option-survival.potionHpPercent` (run 9, [failure record](TutorialSmokeEvidence20261005/run9-failure-pointer-blocked.txt)). The pointer had landed on the window frame and the backdrop only. Runs 8 and 10 passed the same step on the same code, so it is intermittent. The cause is inferred from the code, because the failing run left no screenshot. The guide poll (every 0.25 s) puts a caption band into the window the first time it finds a guide's control, and the window is rebuilt, which replaces its controls (`RefreshTutorialAnchor`, `SyncGuideCaption`). The smoke's `Tap` re-fetches a control after scrolling, but a pointer fired just after the rebuild can land before the new layout has settled.

The fix: when the pointer misses, `Tap` re-fetches the control every frame and waits up to 0.6 s for the pointer to land. If something keeps covering the control it still fails as before, and then leaves a screenshot and the hit list (`pointer-blocked.png`, `pointer-blocked.txt`). After the fix the same tree passed the full smoke three times in a row (runs 11 to 13). Before it, one of three attempts on that tree stopped at this step. PR #54 was merged before this fix, so the fix went in a follow-up PR; put back on `main` at `4fc52dba` (town model PR #57) it passed the full smoke twice more (runs 14 and 15). On the tree with the pit tutorial PR #58 merged the F05 step also passed (runs 16, 18 and 19; run 17 ended before it). Eight runs have passed the F05 step since the fix (11 to 16, 18, 19) and none stopped there, but that is a small sample, so the intermittent failure is not claimed to be gone.

Midnight: the attendance hide lasts only until midnight (KST). A run that crosses 00:00 reopens the attendance window and stalls at the next town step. Run 8 started at 23:53 and failed that way ([screen](TutorialSmokeEvidence20261005/run8-timeout-attendance-after-midnight.png), attendance day 2 of 7), and the same executable passed this step after midnight. This was judged from the screen, the clock and the code and was not reproduced separately. Do not start the smoke just before midnight.

## 6. The pit trial replay — app, fixed

On the tree with PR #58 merged, the full smoke's second launch stopped in the movement lesson of the final replay (`PitReplay`) with `Timed out following the prologue gate: replay movement lesson target=` (run 16, [failure record](TutorialSmokeEvidence20261005/run16-failure-replay-movement-lesson.txt)). PR #58 said it had not checked the replay at the end of the smoke. The failing run left no screenshot, so the stall was reproduced with a clone-only shortcut that plays the replay alone (not in the repository), and `FollowGate` now leaves a screen, the gate state and the open windows when it times out (`gate-timeout.png`, `gate-timeout.txt`). At the timeout the run sat paused in the `Fallen` phase with 0 HP, the dialogue was closed and the gate had no target ([screen](TutorialSmokeEvidence20261005/replay-fallen-stuck.png)).

The cause is in the app. A replay builds a fresh account (`GameStore.NewAccount`) and repeats the trial on it. The `Open the movement option` button of the dialogue after the fall calls `GameStore.UnlockPitMovement`, which first checks that the run is the real account's checkpoint (`Data.guide.tutorialRun`). A replay's run is not that checkpoint, so the call is always refused and the button's handler returns quietly before `ContinueTutorial()`. The phase never moves on to `MovementLesson`. The replay is used by every account that has finished the tutorial and stops at this spot, so it looks like the same defect for players, but entering the replay from the real menu was not checked by hand.

The fix: when the run is a replay, `UnlockPitMovement` grants nothing on the account and returns true. The replay's edict window shows the movement option in the pit lesson by its own rule (`HuntEdictWindow.Disclosed`), so it needs no disclosure on the account. One check was added to `TutorialPitTests` for this case. On the code before the fix only that check fails (`The replay's lesson must be able to open the movement option.`, [result](TutorialSmokeEvidence20261005/editmode-replay-fix-before.xml)); after the fix the 36 related EditMode tests (`TutorialPitTests`, `TutorialProgressionTests`) all pass ([result](TutorialSmokeEvidence20261005/editmode-replay-fix-after.xml)). The fix touches PR #58's app code (`GameStore.Tutorials.cs`), so it is in its own commit and can be split off. The replay alone, run through the shortcut, stopped at the same point after 184.4 s before the fix and passed end to end in 73.4 s after it (back in town without a reward, with the real account's equipment, economy and progression unchanged).

## Not verified

- The pre-fix executable was not re-run on a tree from before PR #58. The cause was judged from the reported failure, code analysis and the pass at the same point after the fix. Only the v3 acceptance smoke was run on pre-fix code, for the comparison above. After #58 the v2 survival lesson and that v3 acceptance smoke are no longer on `main`, so they cannot be checked again.
- On the follow-up PR's tree (`main` at `945fa46f` plus this PR) only the related EditMode classes (`TutorialPitTests`, `TutorialProgressionTests`, 36 tests) were run. The full EditMode suite and the rest of the seven classes above were not run on this tree (the 110 results are from the `d1d762fb` tree). The three static UI checks (`check_ui_contract.py`, `test_ui_contract.py`, `check_ui_refresh.py`) and the full tutorial smoke were run. The other smokes were not, nor was the shared-UI smoke (`-hellscriptSharedUiSmoke`), which walks every group's picker with a legacy account.
- The replay fix was checked only on the smoke's account, marked `edictLegacyAccess=true`. On a non-legacy account whose edict options are disclosed by progress (for example one that finished the tutorial before PR #58), it was not checked that the replay's edict window shows and saves the movement option. Entering the replay from the real menu was not opened by hand either.
- The cause of the clean shutdown of the player during the first rift in run 17 is unknown. It did not appear in runs 16, 18 and 19, which passed the same stretch; an external termination is suspected but was not shown.
- The cause of the `Tap` settling fix is inferred from the code and there is no screenshot of the failing moment. The evidence is a small sample (one failure in three attempts before, eight runs past the F05 step after, on three trees), so the intermittent failure is not claimed to be gone.
- The real screen of a new account after this change was not opened by hand. It was checked through the v3 acceptance smoke's HP lesson and through `Quick` returning the same values (a record from then; the v3 prologue is no longer used after PR #58).
- In the smoke fixture the picker reads `Current settings` while the lesson line says `Balanced supplies`. The fixture is a hybrid account (a fresh hero under a legacy flag). It looks like the new hero's automatic potion buying being off, which matches no preset, but that was not confirmed and it was not changed.
- macOS synthetic pointer verification only; not a physical mobile device and not a user-comprehension test.
