# 다중 시드 밸런스 시뮬레이션 러너 개발 기록

작성일: 2026-09-10 · 갱신: 2026-09-10 보고서 저장과 단계 훑기 추가

## 적용 범위

`Assets/Plans/next-development-plan.md`의 P1 항목에 따라 6개 추천 빌드를 여러 시드에서 자동으로 돌려 클리어율·평균 시간·사망 원인을 모으는 러너를 `BuildIntegrationValidation`에 추가한다. 기존 `Compare`의 읽기 전용 비교 보고서는 그대로 두고 새 진입점을 따로 만들었다.

## 러너의 동작

`RunMultiSeedBalanceSimulation(seedCount, stage)`는 직업 3종 × 변형 2종의 6개 구성을 각각 `seedCount`개의 시드로 실행한다. 시드는 `54321 + 시드번호 × 1337 + 직업 × 97 + 변형 × 31`로 만들어 재실행에서 같은 결과를 얻는다.

각 시도는 새 계정을 만들어 레벨 30, 가방 100칸으로 맞추고 기존 `Sets` 표의 8부위를 생성해 장착한다. 전설 지정이 없는 칸은 희귀 등급으로 만든다. 이후 `CombatSimulation`을 고정 틱으로 최대 10,000틱까지 돌리며 클리어·실패·포탈·길찾기 오류에서 멈춘다.

결과는 구성별로 클리어 수, 실패 수, 클리어율, 평균 클리어 시간, 평균 초당 피해와 사망 원인 분류를 담는다. 사망 원인은 실패·시간 초과·길찾기 오류의 세 가지로 나눈다. 자원 부족 집계는 기존 `resourceChecks` 값을 그대로 옮긴다.

## 보고서 저장과 단계 훑기

`RunBalanceSweep`은 여러 단계를 순서대로 돌려 하나의 JSON 보고서로 모은다. 편집기의 **HELLSCRIPT > 밸런스 시뮬레이션 실행** 메뉴와 배치 실행에서 같은 함수를 사용한다. 기본값은 계획의 빌드당 30시드와 1·10·20·30단계다.

| 실행 인자 | 뜻 |
|---|---|
| `-hellscriptBalanceSeeds` | 구성당 시드 수. 기본 30이다. |
| `-hellscriptBalanceTiers` | 쉼표로 구분한 단계 목록. 기본 `1,10,20,30`이다. |
| `-hellscriptBalanceOutput` | 보고서를 쓸 폴더. 기본 `Artifacts/Validation/BalanceSweep`이다. |

`JsonUtility`는 `Dictionary`를 저장하지 못하므로 사망 원인은 보고서에 쓰기 전에 목록으로 펼친다. 이 변환을 빠뜨리면 사망 원인이 조용히 사라진다. 보고서는 단계를 하나 마칠 때마다 다시 쓰므로, 긴 훑기가 중간에 멈춰도 끝난 단계는 남는다.

시드는 시드 번호·직업·변형에서만 만들고 단계는 넣지 않는다. 따라서 모든 단계가 같은 지형을 다른 난이도로 반복한다. 단계 사이의 차이를 지형 차이로 해석하지 않도록 이 사실을 보고서의 `scope`에 적었다.

## 검사

`BuildIntegrationValidationTests`는 구성마다 시드 2개, 1단계로 러너를 돌려 6개 요약이 모두 나오고 시도 수가 맞으며 길찾기 오류가 없는지 확인한다. 이 검사는 예외 없이 도는지를 보는 안정성 검사이며 밸런스 판정이 아니다.

검사가 `Hellscript.Editor`의 러너를 호출하므로 `Hellscript.Tests.asmdef`에 해당 어셈블리 참조를 추가했다. 참조가 없으면 검사 어셈블리 전체가 컴파일되지 않는다.

## 실제 실행 확인

진입점이 보고서를 만드는지 확인하기 위해 구성당 2시드로 1단계와 10단계를 실행했다. 12개 요약을 얻었고 오류는 없었다. `Artifacts/Validation/BalanceSweepSmoke/balance-sweep.json`에 결과를 보존했다.

이 실행에서 1단계는 6구성이 모두 2판을 클리어했고, 10단계에서는 궁수 변형 2가 2판 중 1판, 마법사 변형 2가 2판 모두 실패로 기록되었다. **구성당 2판은 밸런스를 판단할 표본이 아니다.** 이 수치는 러너와 보고서가 작동한다는 증거일 뿐이며 난이도 결론으로 사용하지 않는다.

사망 원인이 보고서에 남는지도 함께 확인했다. `Dictionary`를 그대로 직렬화하면 이 항목이 조용히 사라지므로 변환 여부를 실행으로 검증했다.

## 읽는 법

이 표는 레벨 30 영웅이 아이템 레벨 30의 8부위를 갖춘 채 기존 규칙 편집기의 추천 설정으로 싸운 결과다. 사냥 칙령 v0.2는 꺼져 있었다. 시드는 직업·변형에서만 만들어지므로 네 단계는 같은 지형을 다른 난이도로 반복한 것이다. 자연 성장·실제 드롭·물약 정책 조정·실기기는 반영하지 않았다. 아래 관찰은 이 조건 안에서만 성립한다.

| 관찰 | 근거 |
|---|---|
| 1단계는 여섯 구성 모두 안정적이다. | 86.7~96.7% 클리어. |
| 10단계는 다섯 구성이 계획의 완료 기준인 70% 이상이다. | 전사 96.7·100%, 궁수 80·83.3%, 마법사 변형 1 73.3%. |
| 마법사 변형 2(연쇄 제어)는 10단계에서 3.3%로 나머지와 동떨어져 있다. | 30판 중 1승. 20·30단계는 0승. 기존 [빌드 비교 기록](Build_Integration_Expansion.md)의 시간 초과 관찰과 방향이 같다. |
| 20단계부터 모든 구성이 급격히 꺾인다. | 6.7~30%. |
| 30단계는 어느 구성도 클리어하지 못했다. | 0/30 × 6. 고정 장비 대비 적 성장이 앞선다는 신호다. |
| 자원 부족 집계는 구성 간 비교에 쓸 수 없다. | 회오리 유지 구성은 매 틱 비용 검사를 쌓아 수백~수천이 되고, 마법사 변형 2는 0이다. 집계 정의를 바꾸기 전까지 참고값이다. |

이 결과는 러너가 만든 첫 측정이다. 밸런스 조정의 근거로 쓰기 전에 마법사 변형 2의 실패 경로를 [사망 원인 분석](Defeat_Analysis_Expansion.md)으로 들여다보고, 20·30단계에는 해당 단계에서 실제로 얻는 장비 수준을 넣어 다시 돌려야 한다.

## 남은 범위

| 남은 항목 | 내용 |
|---|---|
| 완료 기준 해석 | 계획의 ‘10단계에서 클리어율 70% 이상’을 여섯 구성 가운데 다섯이 만족했고 마법사 변형 2가 만족하지 못했다. 한 번의 측정이며 밸런스 검증 완료로 해석하지 않는다. |
| 마법사 변형 2 | 10단계 3.3%의 원인을 사망 원인 분석과 규칙 판단 기록으로 확인해야 한다. |
| 높은 단계 장비 | 20·30단계는 해당 단계에서 실제로 얻는 아이템 레벨을 반영해 다시 측정해야 한다. 고정 레벨 30 장비의 결과를 그 단계의 난이도 결론으로 쓰지 않는다. |
| 평균 초당 피해 | `avgDps`는 클리어한 시도의 누적 피해를 누적 시간으로 나눈 값이며 시도별 초당 피해의 평균이 아니다. 해석을 위해 누적 시간과 누적 피해를 보고서에 함께 남겼다. |
| 자원 부족 집계 | `totalResourceStarvations`는 기존 `resourceChecks`를 그대로 옮긴 값이다. 자원 때문에 실제로 스킬을 건너뛴 횟수와 같은지는 별도로 확인해야 한다. |
| 실패 판정 | 사망 원인은 실패·시간 초과·길찾기 오류의 세 가지로만 나눈다. 어떤 적이나 상황에서 죽었는지는 [사망 원인 분석 기록](Defeat_Analysis_Expansion.md)의 창 기록과 아직 연결하지 않았다. |
