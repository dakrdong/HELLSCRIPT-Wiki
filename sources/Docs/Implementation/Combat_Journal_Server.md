# 균열 전투 기록과 서버 분석 수집

갱신일: 2026-09-25

영어판: [Combat journal and server analytics](Combat_Journal_Server.en.md)

## 플레이어가 보는 기록

균열 입장 화면의 **전투 기록** 버튼을 누르면 계정의 최근 100회 기록을 볼 수 있다. 목록은 완료 시각의 최신순이며, **모두 / 승리만 / 패배만** 목록상자로 결과를 선택한다. 각 행에는 기기 현지 시각과 UTC 오프셋, 직업, 균열 단계, 전투 시간, 종료 사유가 표시된다. 과거 기록에 시각이나 결과가 없으면 미기록으로 표시한다. 과거 결과 문구를 번역하거나 추측해서 승패를 만들지 않는다.

패배에는 사망·시간 초과·보스 처치 전 귀환이 포함되며 종료 사유로 구분한다. 보스를 처치하고 전리품 회수만 중단한 경우에는 기존 전투 결과대로 승리를 유지한다. 훈련은 실제 균열 기록과 분석 대기열을 만들지 않는다.

전투 중에는 기존 생명력·물약·스킬 HUD 위의 하단 영역에 최근 행동을 실시간으로 표시한다. 좁은 화면에서는 들어가는 수만큼의 최신 문장을 표시하고 긴 문장의 미리 보기만 줄인다. 완료 후 상세 화면의 **문자 로그 보기**에서는 처음부터 시간순으로 100줄씩 읽을 수 있다. 기존 전투 요약, 마지막 5초의 피격·불발 분석, 당시 장비와 설정도 유지한다.

기록은 실제 판단과 결과에서 작성한다. 다음 내용이 같은 순번과 전투 시각으로 연결된다.

- 이동·정지, 목표와 목적지, 거리·이동 정책, 해당 판단의 조건과 규칙을 기록한다.
- 기본 공격과 스킬의 선택·준비·발동·중단, 자동 사용 조건과 플레이어 입력을 구분한다. 재사용 대기·자원 부족·사거리 제한·위치 확보 실패도 남긴다.
- 적의 공격·장판 예고는 남은 준비 시간과 목표 위치를 남긴다. 제어 효과로 공격이 중단되거나 보스가 격노한 경우도 기록한다.
- 적중과 피격에는 스킬·효과 출처, 대상, 원래 시전 ID, 실제 HP 손실과 보호막 흡수를 남긴다. 피해량과 과잉 피해를 같은 수치로 해석하지 않는다.
- 처치, 보스, 상자, 물약, 장비·룬·재화 획득과 설정 변경을 기록한다.
- 종료 문장에는 결과·시간·처치·획득 골드를 적는다. 사망이면 실제 마지막 구간의 HP 손실, 가장 큰 피격원과 관측된 스킬 대기 사유를 덧붙인다. 원인을 관측하지 못한 구간은 추정하지 않는다.

## 소유권과 저장

`CombatSimulation`의 실제 판단·이동·피해·보상 경로가 `CombatJournal`을 기록한다. 화면은 기록을 읽기만 한다. `CombatHistory.Capture`의 종료 스냅샷은 현재 장비나 진행 중인 버퍼와 분리한다. 저장 스키마는 **15**이며 기존 기록은 그대로 읽는다.

`GameStore`가 계정 파일을 성공적으로 저장한 뒤 `CombatJournalArchive`가 파생 파일을 만든다. 계정 저장이 실패한 상태에서 전송 파일을 만들지 않는다. 파일 저장 실패 시 계정에 남은 전체 기록으로 다음 저장 때 다시 시도한다. 성공한 뒤에는 계정 안의 전체 이벤트를 비우고 개별 파일에서 읽어 계정 저장 크기를 줄인다. ACK 직후 앱이 종료되어도 이미 만든 파일의 동일한 바이트를 재전송한다.

| 위치 | 용도와 보관 규칙 |
| --- | --- |
| `<save directory>/combat-records/<runId>.json` | 한 전투에 하나의 JSON 파일을 만든다. 읽을 수 있는 문장과 구조화된 원본을 함께 담고, 최근 100회에 없는 파일을 삭제한다. |
| 계정의 `records` | 최근 100회의 요약·상세 분석·당시 설정을 보관한다. 파일로 내보내지 못한 기록에는 이벤트도 남긴다. |
| `<save directory>/combat-outbox/<runId>.json` | 서버 전송 대기 원본이다. 플레이어 기록의 100회 정리와 분리하며, 일치하는 ACK를 받은 파일만 삭제한다. |
| `*.json.rejected` | 서버가 잘못된 스키마·용량·동일 ID의 다른 본문을 거절한 원본이다. 보존하고 다음 전투 전송을 진행한다. |

한 전투의 상세 이벤트는 최대 20,000개이다. 초과 시 시작과 최신 구간을 보존하고 생략 수·순번 공백을 명시한다. 전체 피해·획득 합계는 별도 집계를 유지한다. 이동 이유에는 실제로 적용된 개별 이동 정책을 사용하고 생존 회피·스킬 위치 조정을 구분한다. 오래된 판단을 현재 발동 조건으로 다시 사용하지 않는다. 이동은 상태 전환과 2초 간격으로, 반복되는 같은 판단은 4초 간격으로 기록한다. 이 파일은 매 프레임의 위치 재생 파일이 아니다. 이벤트의 `damageEvents`, `rules`, `builds`, `edicts`는 필요한 경우에만 원소 하나를 갖는 배열이다. Unity가 빈 참조를 기본 객체로 복원하는 특성 때문에 불필요한 스냅샷이 늘어나지 않도록 하고, 파일은 공백을 줄인 JSON으로 저장한다.

분석 대기열은 거절 보관본을 포함해 1,000개 또는 256 MiB로 제한한다. 한도에 도달해도 플레이어 파일을 만들며, 최근 100회 안의 미전송 원본은 다시 시도한다. 서버가 장기간 연결되지 않아 내보내지 못한 기록이 100회 보관 범위에서도 밀리면 `combatTelemetryLossCount`와 다음 기록의 `LOCAL_EXPORT_LOSS`로 누락을 표시한다. 이 경우 전체 플레이가 수집되었다고 보고하면 안 된다.

## 분석 항목과 신뢰 경계

| 항목 | 기록하는 값 |
| --- | --- |
| 사용자·캐릭터 | 서버가 인증 세션으로 결정하는 계정 ID, 클라이언트의 로컬 계정 식별자, 캐릭터 ID·직업·시작/종료 레벨, 로컬 도전 순번을 구분한다. 실명이나 광고 식별자는 수집하지 않는다. |
| 실행 환경·콘텐츠 | 앱 버전·빌드 GUID·플랫폼·저장 스키마·아이템/지도 버전·균열 단계·지도 지문·시드가 포함된다. |
| 시각·진행 | 클라이언트 UTC 시작/종료 시각, 전투 시뮬레이션 시간, 기존 참여·피로도 시간, 재개 횟수와 관측 시작점을 기록한다. 서버 수신 시각은 서버에서 별도로 쓴다. |
| 출전 구성 | 시작 빌드·스킬 슬롯/랭크/옵션·사냥 칙령·장비 인스턴스·슬롯 강화·룬 구성·물약 상태와 종료 시 설정이 포함된다. 변경 이벤트에는 당시 빌드도 남는다. |
| 성과·보상 | 승패·종료 사유·처치·보스 처치·획득 골드·장비 수·룬 수, 장비와 재화 드롭별 회수/무시 여부와 실제 아이템 스냅샷을 저장한다. 골드는 지갑 차이가 아닌 `RiftEarnings`의 실제 지급량이다. |
| 전투·이상 징후 | 사건 순번, 시전·대상·규칙 ID, 위치, HP·자원, 피해 계산 값, 최종 5초 분석, 상세 생략·재개·내보내기 누락과 시계 신뢰 여부를 남긴다. |

클라이언트 자료의 `trust`는 `client_observed`이다. SHA-256은 재전송 본문의 일치 여부를 확인하며 치팅 방지 서명이 아니다. 서버는 인증 계정과 전투 ID로 중복을 막고, 같은 ID의 다른 본문을 감사 기록으로 남긴다. 불가능해 보이는 시간·승패·보상은 조사 신호이며 자동 제재 근거로 확정하지 않는다.

기존 `AuthoritativeRiftVerifier`는 서버가 소유한 입장 스냅샷·시계·시드에서 같은 전투 코드를 재연산한다. 종료 기록의 `server_replay` 사본을 `HuntAuthorityCheckpoint.combatTelemetry`에 넣어 계정·커서와 같은 CAS 저장에 포함한다. 클라이언트 HTTP 경로는 이 신뢰 표기를 허용하지 않는다. 서버 내부 어댑터는 확정된 체크포인트만 `Repository.attach_authority`에 연결해야 한다.

## 서버 연결 준비

`GameController.Telemetry`에 로그인 호스트가 `ICombatTelemetrySession`을 제공해 `Configure`한다. 세션은 HTTPS 주소와 현재의 단기 액세스 토큰을 제공한다. 자격 증명이나 주소를 저장 파일에 넣지 않으며, 설정 전에는 네트워크 전송을 시작하지 않는다. 개발 빌드에서만 loopback HTTP를 허용한다.

`CombatTelemetryUploader`는 POST 후 `accepted`, `runId`, 원본 바이트의 `payloadHash`가 모두 일치할 때만 파일을 삭제한다. 시간 초과·인증 오류·일시적 서버 오류에는 최대 300초의 지수 대기로 재시도한다. 리디렉션은 따라가지 않는다.

`server/combat_telemetry.py`는 표준 라이브러리와 SQLite로 만든 실행 가능한 참조 수신기다. `/v1/combat-runs`에서 인증·크기·스키마·순서·시각·합계 구조를 검사하고, 전투·이벤트·드롭을 한 트랜잭션으로 저장한 뒤 ACK한다. `server/combat_analytics.sql`은 사용자/캐릭터/단계별 승률·시간·골드, 스킬별 피해, 획득 항목과 서버 검증 근거를 조회한다.

운영 서비스의 주소·로그인 세션 어댑터·서버 입장/보상 저장소는 이 작업 시점에 연결되어 있지 않다. 운영 반영 때 TLS·인증·요청 제한·백업·보관 정책과 재연산 워커를 실제 호스트에 연결해야 한다. 로컬 HTTP 검증을 운영 서버 수집 완료로 간주하지 않는다.

## 검증과 전달 범위

검사 결과와 macOS 화면 증거는 `CombatJournalEvidence/`에 기록한다. 원래 작업 폴더의 사용자 변경과 실행 중인 Editor를 보존하고, 최신 `main`에서 만든 별도 작업 폴더에서 Unity 배치 검사와 개발 빌드를 수행한다. macOS 포인터 합성 검사는 모바일 실기기 검사와 구분한다.

브랜치의 문서는 병합할 때 공개 위키에 함께 반영한다. 공개 배포는 검증한 `main`에서만 수행한다.

### 확인한 결과

- Unity Edit Mode 확장 회귀 488/488, 기록·적·보스·번역 보완 155/155, 실제 사망 요약·번역·이동 반응 최종 검사 137/137을 통과했다. 범위가 겹치는 세 실행이며 전체 프로젝트 검사 수로 합산하지 않는다. [검사 결과](CombatJournalEvidence/validation.json)와 [최종 사망 검사](CombatJournalEvidence/editmode-defeat.xml)를 보관한다.
- macOS 개발 빌드는 오류 0건으로 성공했다. 일반 Update에서 기록이 증가하는 것을 확인한 뒤 고정 스텝으로 전투를 진행했다. 결과를 강제하지 않은 1단계 승리에서 시뮬레이션 약 102.8초, 처치 43, 골드 2,276, 장비 5개를 기록했다. 실제 참여 시간과 시뮬레이션 시간은 다른 값으로 저장하며, 이 검사를 실시간 102.8초 플레이로 보고하지 않는다.
- 세로 440×956, 가로 956×440, PC 1600×900·1600×1000·2100×900에서 한국어·영어와 글자 크기 100%·140%를 확인했다. 실시간 하단 로그 20조건과 기록 목록 20조건에서 글자 및 HUD 겹침을 검사했다.
- 실제 전투 1개와 별도로 표시한 목록 검사 자료 99개로 100행을 검증했다. 포인터 레이캐스트와 누름·뗌·클릭으로 균열의 진입 버튼, 세 결과 필터와 상세 로그를 열었다. 임시 목록 자료는 최종 저장 전에 제거했다.
- 별도 앱 실행에서 전체 기록을 다시 불러왔다. 101번째 기록의 오래된 파일 삭제와 전송 대기 보존, 저장 실패·대기열 한도·ACK 후 종료·거절 후 종료는 Edit Mode에서 확인했다.
- Unity 클라이언트 → localhost HTTP 수신기 → SQLite 저장 → ID·SHA-256 일치 ACK → 대기 파일 삭제를 확인했다. 서버 검사 9/9, 실제 수신 자료에 대한 분석 SQL 5개를 통과했다. [실행·수신 근거](CombatJournalEvidence/runtime.json)에 파일 크기와 해시를 기록한다.
- 공통 UI 검사 및 회귀 9/9, 위키 build/check·Python 10/10·JavaScript 검사를 통과했다. 모바일 실기기와 운영 서버 연결은 확인 범위에 포함하지 않는다.
