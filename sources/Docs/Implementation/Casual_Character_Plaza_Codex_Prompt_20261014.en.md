## Background
- The game art moves from dark gothic to a bright casual look (style D, ages 12+). Each class now has two genders, so there are six heroes (warrior, ranger, mage, each male and female). There is no nickname field (the nickname is created later, in a tutorial once the player has progressed).

## Screen requirements (mockup summary; exact numbers in the README)
- Scene: the six heroes stand in one town scene, each in their own spot: the male and female warrior on the tavern terrace in front, the rangers at the fruit stall in the middle, the mages at the magic shop by the fountain in the back. Landscape (956×440) and PC (1152×648) cover the frame with the whole scene. Portrait (440×956) uses the scene redrawn tall; the three crests on the right (mage, ranger, warrior from top to bottom, 65 px, centred on the screen height, 112 px apart) move the camera to that class's pair and zoom in (0.9 s). Choosing a hero makes the camera follow its class.
- The top has only "‹ 타이틀" and the heading "나만의 모험가를 골라요". There are no motion or language buttons on this screen (user decision: the game always plays the motion and the language is changed in Settings). This screen does not read TitleSession.MotionEnabled and always plays. The two buttons on other screens are out of scope.
- Unselected heroes look inactive (saturation .45, brightness .88). Tapping one restores its colour, adds a white outline with a class-coloured glow and puts a class name tag (class name + gender glyph) at its feet.
- Choosing a hero that has not been created shows a green + button above its head. Tapping it hides the painted hero with a background patch, stands the cheer pose (cheer_*) in its place for 1.8 seconds with a speech bubble line that fits the hero, then returns to the original pose; creation is done and a Lv.1 pill plus a person icon appear above the head. The person icon opens the equipped-gear popup (8 slots: weapon, head, chest, hands, feet, belt, amulet, ring). The popup shows what the hero actually wears, drawn with the shared parts.
- Choosing a created hero shows a green "PLAY" at the bottom centre. Pressing it switches the hero to the battle-ready pose (fight_*, equipped weapon) with a personality line, turns the button into a disabled "Entering…" and continues into the existing entry (CommitEntryCharacter -> EnterPlaza(true)).
- While creating or entering, taps on other heroes and crests are ignored.
- With a rift in progress only the hero that owns it can be chosen; the rest show greyscale with a padlock (existing LockedHero rule).
- Nothing is saved while previewing. Save only when "+" creates a hero and when Play confirms entry. On a failed save restore the previous state and show a toast (the existing SaveEntryCharacter way).
- Keep the PC keys (left/right selects, Esc returns to the title, Enter starts when no button is focused) and extend them to cycle the six heroes (front row male and female warrior, middle male and female ranger, back male and female mage).
- Hero lines (created / entering): male warrior "좋아, 한판 붙어 보자고!" / "다 덤벼라! 앞장은 내가 선다!", female warrior "배도 채웠겠다, 덤벼!" / "몸 다 풀렸어. 전부 날려 줄게!", male ranger "흥정 끝! 이제 사냥 시간이야." / "한 발이면 충분하지!", female ranger "조용히, 확실하게. 따라와." / "숨 고르고… 놓치지 않아.", male mage "책에 다 나와 있었다고!" / "계산 끝. 불꽃 맛 좀 봐라!", female mage "반짝반짝, 마법 시작이야!" / "자, 마법 쇼를 시작해 볼까?" ## Decisions
Decision 1: settled by the user on 2026-10-14: six saved heroes (Option A, matches the mockup).
- Structure: AccountSave.heroes always holds all six heroes. Indexes 0-2 are the male warrior, ranger and mage exactly as today; 3-5 are the female warrior, ranger and mage. Then assumptions such as heroes[(int)heroClass] stay true for the male heroes, and the hero id (HeroSave.id) and HeroClass stay as they are. Add gender (default male) and created to HeroSave, and add one place that finds a hero index from (class, gender). An uncreated hero exists in the save as a default hero; "+" turns created on and starts that hero's tutorial share the existing way.
- Migration: raise the save schema (GameStore.MaximumSchemaVersion, today 22 with D4 on and 21 in legacy mode). On load, grow a three-hero save to six (the three female heroes are default heroes built like NewAccount does) and mark the existing three as male and created. Keep the original as .schema<N>-before-six-heroes.json like the existing migrations. Change the heroes.Count!=3 check in Read to accept only 3 (an old save to migrate) or 6. The D4 legacy developer mode (schema 21) neither reads nor writes the new save and refuses it while preserving the original (the existing D4 refusal way).
- Audit: classify and change the places that assume "hero index = class index" (selectedHero 245 places, heroes[ ] 150 places, and those of the 218 class-index casts that are really hero indexes). The places I found: GameStore.cs lines 33, 66 and 422, GameStore.CharacterSwitch.cs, Tutorials.cs Switch/Take/Park and GuideTutorial.WarriorIndex, PuzzleTutorial.cs 229 and 240, CombatSimulation.ClassSkillValidation.cs 32, CombatSimulation.SkillPreview.cs 30, CharacterSelectionState.LockedHero. Account-wide loops (daily quests, offline rewards, telemetry, codex, ...) must not touch uncreated heroes. Existing screens that list heroes (the in-game character switch, class buttons, ...) show only created heroes. Fix test assumptions of exactly three heroes.
- Stages (recommended): PR 1 = save structure, migration and tests. The old selection screen shows only created heroes so it behaves as before, and a new account still starts with all three male heroes created as today. PR 2 = the new screen and the new-account default (Decision 2). Write the audit results and the staged plan in the PR description and go ahead (do not wait for an answer). If the impact turns out much larger than expected, stop and report.
- Make the screen read a single "six slots (class, gender, created, level, rift lock, equipped gear)" list instead of the save structure. Until PR 1 is done, fill the slot provider with the mockup's example account (male warrior Lv.24, female ranger Lv.17, female mage Lv.31 with a rift in progress, the other three not created) as a fake and build the screen, state rules and tests first.
Decision 2: first start of a new account (default): EnterFirstStart keeps entering the male warrior at once. From PR 2 a new account starts with only the male warrior created and the other five show + (to start with the male ranger and mage created as well needs the user's confirmation). This screen first appears at the second login.
Decision 3: the three existing heroes of an existing account move over as male and created (default). Do not turn a level-1 hero without progress back into +.
Decision 4: art status. The scenes and pose pictures are Codex originals; the hero layers are cut from the scene with macOS Vision, so they are not native alpha. Register them in the game as replaceable development art (productionApproved false) and write the processing into the provenance. Tell the user that the female warrior's outfit (bare midriff) needs a 12+ rating check.
Decision 5: fonts. Add no new font in this task. Use the fonts UiTheme owns; if the Jua and Noto Sans KR chosen by the skill window casual skin task are not on main yet, build with the current fonts.
Decisions 2-5 proceed with the defaults above and are listed in the report.
