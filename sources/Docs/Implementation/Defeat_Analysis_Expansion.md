# 사망 원인 분석·사망 직전 기록 개발 기록

작성일: 2026-09-10 · 갱신: 2026-09-10 전투 루프 연결과 검사 완료

## 적용 범위

`Assets/Plans/next-development-plan.md`의 P3 항목에 따라 사망 직전 구간의 피격 집중과 스킬 불발 원인을 읽는 화면을 만든다. 자료 구조와 집계 함수, 결과 화면을 먼저 추가한 뒤 전투 루프와 규칙 판단에 기록을 연결했다.

기존 전투 계산·난수·저장 형식은 바꾸지 않았다. 기록은 메모리에만 남기며 기존 집계 필드와 훈련 비교 판정은 그대로 사용한다.

## 추가한 자료 구조

`CombatStatistics.cs`에 사망 직전 구간을 읽기 위한 형식을 추가했다.

| 형식 | 담는 내용 |
|---|---|
| `CombatTickSnapshot` | 한 틱의 시각, HP·최대 HP·자원, 총 피격 피해와 HP 손실, 그 틱의 피격원 목록과 불발 목록이다. |
| `TickDamageSource` | 피격 하나의 출처 ID·이름, 피해와 HP 손실, 보스 여부와 장판 여부다. |
| `BlockedSkillAttempt` | 사용하지 못한 스킬의 번호·ID·이름, 불발 사유(`BlockReason`)와 상세 문구다. |
| `DefeatAnalysis` | 창 구간의 총 피해·HP 손실, 피격원별 합계와 비율, 불발 사유별 횟수와 원본 시간대다. |

`BlockReason`은 재사용 대기, 자원 부족, 군중 제어·침묵, 행동 잠김, 기타의 다섯 가지다. 화면에 표시할 한국어 문구는 집계 단계에서 붙인다.

## 기록과 집계

`CombatStatistics.RecordSnapshot`은 틱 기록을 목록에 넣고 `RingBufferCapacity` 300개를 넘으면 가장 오래된 항목을 버린다. 고정 틱이 0.05초이므로 300개는 15전투초에 해당한다. 계획 문서의 ‘60Hz에서 5초’와 실제 틱 간격이 다르므로, 화면이 사용하는 구간은 개수가 아니라 시간으로 자른다.

`BuildDefeatAnalysis(catalog, windowSeconds)`는 마지막 기록 시각에서 지정한 시간만큼 거슬러 올라간 구간을 고르고, 그 안에서 피격원별 피해·HP 손실·타격 수를 합산한다. 비율은 구간의 HP 손실 합계를 분모로 쓰되 손실이 0이면 피해 합계를 사용한다. 불발은 스킬 번호와 사유를 묶어 횟수를 센다. 창 구간에 기록이 없으면 보존된 전체 기록을 사용한다.

`CombatSimulation.RecordTickIncomingDamage`는 기존 `Hurt`의 피해 확정 지점에서 호출된다. 시전자 ID로 적을 찾아 보스·일반 적의 이름을 붙이고, `N10`·`ENEMY_GROUND`·`ENEMY_ATTACK`은 고정 문구로 표시한다.

## 전투 루프 연결

`Tick`은 일시정지·포탈·종료·전리품 정리를 걸러 낸 뒤 전투 본문을 `TickCombat`으로 분리하고 `try`·`finally`로 감쌌다. 전투 본문에는 사망 정산·길찾기 오류 등 중간 반환이 여러 개 있는데, 우리가 가장 알아야 하는 틱이 바로 영웅이 죽는 틱이므로 마지막 문장이 아니라 `finally`에서 기록을 마감한다. 일시정지와 전리품 정리 틱은 기록하지 않는다.

한 틱에 쌓인 피격과 불발은 `RecordTickTelemetry`에서 한 개의 스냅숏으로 합쳐 링 버퍼에 넣고 임시 목록을 비운다. 피격도 불발도 없는 조용한 틱은 공유하는 빈 목록을 사용해 추가 할당을 만들지 않는다. 전투 틱 밖에서 피해가 들어올 수 있는 검사용 경로를 대비해 임시 목록은 512개로 제한한다.

## 불발 기록 연결

규칙 판단의 모든 차단 사유는 `RecordDecision` 한 곳을 지나므로 여기에서 기록한다. 스킬 규칙만 대상으로 하며 사유를 다음과 같이 옮긴다.

| 판단 코드 | 기록 사유 |
|---|---|
| `COOLDOWN` | 재사용 대기중 |
| `RESOURCE` | 자원 부족 |
| `ACTION_LOCK`, `CHANNELING` | 행동 잠김 |
| `LEVEL_LOCK` | 기타 방해 |

`RANGE`, `LINE_OF_FIRE`, `NO_TARGET`, `LANDING`, `CONDITION`, `EFFECT_ACTIVE`는 기록하지 않는다. 이들은 스킬이 잠긴 것이 아니라 위치·대상·조건의 문제이므로 잠금 원인으로 함께 세면 사망 원인을 잘못 읽게 된다.

`BlockReason.CrowdControl`은 정의만 있고 기록되지 않는다. 현재 영웅에게는 기절·침묵 상태가 없다. 해당 상태를 도입할 때 연결한다.

## 저장 형식

링 버퍼는 `[NonSerialized]`이므로 저장 파일에 들어가지 않는다. 300개 스냅숏을 직렬화하면 체크포인트가 커지고 기존 검사가 대조하는 계정·전투 JSON이 달라진다. 사망 원인 분석은 같은 실행 안에서 읽는 자료이므로 메모리에만 남긴다. 저장을 불러온 전투는 빈 창에서 다시 쌓기 시작한다.

## 화면

결과 화면이 실패이고 훈련이 아닐 때 **사망 원인 분석 (최근 5초 기록)** 버튼을 표시한다. 분석 화면은 5초간 총 피격 피해와 초당 피해, HP 손실을 먼저 보여 준 뒤 피격원을 피해 순으로 나열하고 불발 사유를 횟수와 함께 표시한다. 하단의 **사냥 칙령 수정하러 가기**로 행동 설정 화면에 바로 들어간다.

기록이 없으면 ‘기록된 5초간의 상세 피격 데이터가 없습니다’를 표시한다. 없는 자료를 추정해 채우지 않는다.

## 검증

전체 Edit Mode 검사 **1,037개**가 통과했다. 이 중 사망 원인 분석 검사는 6개이며 다음을 확인했다.

| 검사 | 확인한 결과 |
|---|---|
| 저장 격리 | 40틱을 진행한 뒤 전투 JSON에 링 버퍼와 스냅숏이 들어가지 않았고 계정 JSON도 그대로였다. 저장을 다시 읽으면 빈 창에서 시작했다. |
| 틱당 한 개 기록 | 120틱에서 스냅숏 수가 집계 틱 수와 같았고, 마지막 스냅숏의 시각과 HP가 현재 전투 상태와 일치했다. 350틱을 더 진행하자 300개에서 가장 오래된 기록부터 밀려났다. |
| 피격원 표시 | 적용한 피격이 ‘적 일반 공격’ 출처로 집계되고 피해 순으로 정렬되었다. |
| 불발 사유 | 자원 부족과 재사용 대기만 기록되고 사거리·대상 없음은 기록되지 않았다. 사유 문구와 마지막 상세 문구가 함께 남았다. |
| 창 자르기 | 같은 기록에서 1초 창이 5초 창보다 적은 스냅숏을 고르고 각 창의 길이가 요청한 시간을 넘지 않았다. |
| 사망 틱 포함 | 치명적인 피격 뒤의 틱에서도 기록이 남았고 마지막 HP가 0으로 집계되었다. |

`Artifacts/Validation/defeat-analysis-editmode.xml`에 보고서를 보존했다. 이 폴더는 저장소에 포함하지 않는다.
